## 7. 你具体做了什么

建议拆成 4 层讲：

### 数据层

- 基于 `open-compass/LawBench` 官方数据组织任务目录
- 梳理 20 个任务的认知层级、来源、指标、任务类型
- 抽取可用于页面展示的样本和说明信息

### 模型接入层

- 把项目的调用接口改成 DeepSeek
- 支持 `zero_shot` 和 `one_shot`
- 对单选题结果做 `A/B/C/D` 归一化，便于自动评测

### 系统层

- 前端展示任务总览、数据集设计、样本、Prompt 结构
- 后端提供任务概览、单条推理、批量评测、历史记录接口
- 支持把运行结果保存下来，方便演示和后续对比

### 部署层

- 补齐容器化部署文件
- 把项目推到 GitHub
- 部署到腾讯云 CloudBase 云托管，形成公网访问地址

## 8. 项目难点怎么讲

不要只说“接了个 API”，建议这样说：

### 难点 1：基准数据到交互系统的映射

LawBench 本身是 benchmark 数据和脚本，不是现成产品。我做的核心工作之一，是把任务级、样本级、运行级结构抽象出来，变成前端可以展示、后端可以调用的一套统一对象。

### 难点 2：在线评测稳定性

LawBench 任务类型很多，不同任务的输出形式差异很大。我先优先落地单选题任务，因为这类任务可以做稳定归一化和自动评分，适合在线演示。

### 难点 3：从本地到云端部署

我需要把本地跑通的前后端系统容器化，并接入 GitHub 和腾讯云云托管，形成公网可访问的作品链接。

## 9. 演示顺序

给 HR 或面试官演示时，按这个顺序最稳：

1. 打开首页，先讲这是中文法律 benchmark 演示平台。
2. 指向总览区，说明任务数、每任务样本数、zero-shot/one-shot、认知层级分布。
3. 下滑到“数据集设计说明”，讲你不是做了个聊天页，而是在展示 benchmark 设计。
4. 左侧选择一个任务，优先选支持在线评测的单选任务：
   - `1-2`
   - `2-4`
   - `2-8`
   - `3-6`
5. 跑一次单条推理，展示前后端和模型调用已经打通。
6. 再跑一次 `3-5` 条的小批量评测，展示自动打分能力。
7. 展示历史记录，说明结果是可复现、可保存、可对比的。

## 10. 面试官可能会问什么

### 1. 为什么选 LawBench

回答：

因为我的目标不是做泛化聊天 demo，而是做一个有明确场景约束、有评测标准的中文法律大模型展示项目。LawBench 本身有任务划分、数据来源和评价指标，适合做工程化展示。

### 2. 你和直接跑官方脚本有什么区别

回答：

官方脚本更偏离线评测，而我做的是工程化封装，把数据结构、任务选择、样本预览、在线推理、自动评测和云端部署都整合进了一个前后端系统，更适合展示模型能力和工程能力。

### 3. 为什么只优先支持部分任务在线自动评测

回答：

因为我先优先落地最稳定的任务类型。LawBench 里有生成题、抽取题、多选题、回归题，自动评测难度不一样。为了保证在线演示稳定性，我先支持了最适合归一化和打分的单选任务，后续可以再逐步扩展。

### 4. 这个项目的难点是什么

回答：

难点不只是调用模型 API，而是把 benchmark 数据结构、Prompt 组织、输出归一化、自动评测、页面交互和云端部署整合起来，并且让它适合真实演示。
